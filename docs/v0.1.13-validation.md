# AKRAT v0.1.13 · validation et dépendances

État au 13 novembre 2026. Branche : `v0.1.13-node-autoupdate`. Commit candidat : `331359e4f06f7de73290135ac0f77f73bb9e5230`. Le tag historique `v0.1.12` reste inchangé. La CI complète du candidat et la vérification de la clé officielle ont réussi; le tag/release `v0.1.13` sera créé après cette validation.

## Travaux validés

- La politique locale des relais classe les chemins directs avant les favoris, puis les relais autorisés. À niveau identique, elle tient compte de la latence et évite un changement pour un gain inférieur à 50 ms.
- Les favoris restent soumis aux règles d’autorisation. Un favori indisponible peut être remplacé par un relais autorisé; un relais exclu ne devient pas un secours.
- L’interface Réseau expose cette règle et conserve les préférences dans le coffre.
- L’updater `akrat-node-updater` cible Linux x64. Il réutilise les attestations Ed25519 et la racine de confiance de `akrat-trust`; il vérifie la signature et les empreintes avant installation. Il rejette les régressions de version, les versions non stables en mode automatique et les ressources hors des URLs officielles des assets GitHub AKRAT.
- Commandes disponibles : `check`, `apply --approve`, `auto` et `verify`. Le remplacement est verrouillé et atomique. Relay et Mailbox ont des contrôles de santé; une erreur restaure le binaire et l’état sauvegardé. Les bases Mailbox sont sauvegardées via SQLite en ligne. L’auto-update Mailbox reste désactivé par défaut, jusqu’à opt-in explicite.
- Le paquet Linux comprend les unités systemd service/timer et un exemple de configuration. La politique de mise à jour initiale est manuelle. Aucun nouveau mécanisme concurrent à `akrat-trust` n’a été ajouté.
- La feature HTTP `stream` requise par l’updater est activée uniquement sur `akrat-node-updater`, et non sur le manifeste workspace partagé. Le graphe effectif de `akrat-desktop` confirme qu’il ne reçoit pas cette feature.

## Contrôles locaux

Sur Windows, `cargo fmt --all -- --check`, `cargo check --locked --workspace --all-targets`, `cargo clippy --locked --workspace --all-targets -- -D warnings` et `cargo test --locked --workspace` réussissent. La suite complète compte 123 tests, dont les validations des conversations, des migrations de coffres, des livraisons asynchrones et des transports relais. Les dix tests ciblés de l’updater couvrent la configuration, les URLs d’assets GitHub, la politique stable/manuelle, la réponse de santé, les signatures invalides, la sauvegarde SQLite, une installation avec validation de santé et le retour arrière du binaire/de l’état/de la base après échec.

`cargo audit` termine sans échec, avec six avis déjà autorisés par sa politique. `cargo deny check -W unmaintained -W unsound --hide-inclusion-graph` réussit avec des avertissements de dépendances transitives, dont `rand 0.7.3` dans la chaîne de build Wry et `glib 0.18.5` dans la chaîne Linux GTK. Aucun avis n’a été ajouté à la liste d’exceptions. `cargo machete` et `git diff --check` réussissent également.

Le binaire de signature accepte `--check-key`, qui vérifie que `AKRAT_RELEASE_SIGNING_SEED` correspond à la racine de confiance compilée sans produire de signature. Le workflow de build manuel exécute ce contrôle sur la branche v0.1.13 avant de considérer la publication.

Le binaire Windows a interrogé l’API du dépôt privé avec l’authentification GitHub locale; aucune mise à jour stable plus récente n’était publiée. Le binaire Linux de la CI a été téléchargé et lancé sous WSL; sa CLI affiche les quatre commandes. Ce contrôle ne simule pas un déploiement systemd.

## Banc Linux systemd isolé

WSL Ubuntu 24.04 expose `systemd` comme PID 1 et `systemd-run` fonctionne. L’état global signale `degraded` à cause d’un `console-getty.service` échoué; D-Bus est actif et une unité AKRAT temporaire a pu être démarrée, arrêtée et redémarrée. Aucun service ni fichier d’unité n’a été installé durablement : l’unité de test a vécu dans `/run/systemd/system`, et les fichiers du nœud dans le répertoire temporaire WSL.

Le test `systemd_updates_real_mailbox_and_rolls_back_a_failed_executable`, activé seulement par la feature de développement `systemd-integration`, a passé avec **11 tests sur 11** (`cargo test --locked -p akrat-node-updater --features systemd-integration`). Il a installé les binaires Linux v0.1.12 issus de la release officielle, lancé le Mailbox et AKRAT Relay avec Iroh Relay comme processus enfant sous systemd, puis remplacé les exécutables par ceux de l’artefact CI v0.1.13. Il vérifie les nouveaux PID, la santé du Mailbox, les endpoints HTTP du Relay et d’Iroh, l’exposition du manifeste signé, l’identité de configuration Mailbox inchangée, l’intégrité SQLite, une boîte et une enveloppe persistées. Une racine Ed25519 fraîche est générée en mémoire pour le test; des attestations de test sur les empreintes des exécutables sont signées puis vérifiées, et le contrôle rejette une signature falsifiée. Aucune clé de test n’est enregistrée ni acceptée par le binaire de production.

Le banc rejette aussi un exécutable symbolique pendant la préparation alors que Mailbox est arrêté, et vérifie que le service est relancé et sain après cet échec précoce. Le scénario d’échec signe ensuite un exécutable de test volontairement invalide, vérifie le retour arrière systemd vers le vrai binaire Mailbox v0.1.13, puis vérifie la restauration d’une base SQLite prise avant une modification sentinelle et la conservation de l’enveloppe. Le test appelle la transaction interne après vérification Ed25519 et SHA-256; il ne teste pas la découverte du manifeste depuis l’API distante GitHub au travers de `apply`.

Non couverts par ce banc : épuisement réel du disque (aucun volume à quota isolé n’a été préparé; le disque racine WSL n’a pas été rempli), refus d’écriture via le service systemd updater sous son confinement de permissions, interruption brutale du processus updater, démarrage automatique après redémarrage complet de WSL, Mailbox/Relay fédérés sur Internet et signature avec la racine officielle. L’updater est distribué comme service root; le runner Linux GitHub est `akrat-runner`, non-root, sans sudo, donc le test systemd est exécuté explicitement dans le WSL isolé par root et n’est pas intégré à la CI. Aucun réglage sudoers ni aucune configuration durable du service hôte n’a été changé. WSL n’est pas un VPS Contabo. Ces limites sont séparées de la validation technique locale et ne valent pas validation de production.

## Tests réseau

Le test d’intégration `favorite_relay_can_establish_an_open_p2p_path` vérifie un flux chiffré via un relais favori utilisé comme route commune par les deux endpoints. Iroh sélectionne entre les chemins déjà ouverts; il ne promet pas d’ouvrir automatiquement chaque relais mentionné dans une adresse distante. Le classement des chemins direct/favori/autorisé est vérifié par `relay_path_tiers_keep_direct_paths_ahead_of_favorites_and_allowed_relays`. Le test `endpoint_switches_to_an_allowed_relay_after_home_relay_fails` valide le repli et la livraison après panne du relais initial.

## Portée et limites opérationnelles

macOS n’est pas compilé ni validé. Les tests locaux et le banc systemd ne mesurent pas la disponibilité de relais publics sur Internet. L’updater Linux n’a pas encore été déployé sur un VPS Contabo. La release v0.1.12 ne contient pas d’attestation officielle; son installation ne peut donc pas être validée comme source par le nouvel updater. Le premier passage vers v0.1.13 demande une installation manuelle. Le mode automatique reste désactivé par défaut sur les nœuds critiques. Le banc systemd dans WSL valide des exécutables réels et des redémarrages Linux isolés; il ne démontre pas un déploiement en production.
