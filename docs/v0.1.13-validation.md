# AKRAT v0.1.13 · validation et dépendances

État au 13 novembre 2026. Branche : `v0.1.13-node-autoupdate`. Le tag historique `v0.1.12` reste inchangé. Aucun tag ni aucune release `v0.1.13` n’a été créé pendant cette validation.

## Travaux validés

- La politique locale des relais classe les chemins directs avant les favoris, puis les relais autorisés. À niveau identique, elle tient compte de la latence et évite un changement pour un gain inférieur à 50 ms.
- Les favoris restent soumis aux règles d’autorisation. Un favori indisponible peut être remplacé par un relais autorisé; un relais exclu ne devient pas un secours.
- L’interface Réseau expose cette règle et conserve les préférences dans le coffre.
- L’updater `akrat-node-updater` cible Linux x64. Il réutilise les attestations Ed25519 et la racine de confiance de `akrat-trust`; il vérifie la signature et les empreintes avant installation. Il rejette les régressions de version, les versions non stables en mode automatique et les ressources hors des URLs officielles des assets GitHub AKRAT.
- Commandes disponibles : `check`, `apply --approve`, `auto` et `verify`. Le remplacement est verrouillé et atomique. Relay et Mailbox ont des contrôles de santé; une erreur restaure le binaire et l’état sauvegardé. Les bases Mailbox sont sauvegardées via SQLite en ligne. L’auto-update Mailbox reste désactivé par défaut, jusqu’à opt-in explicite.
- Le paquet Linux comprend les unités systemd service/timer et un exemple de configuration. La politique de mise à jour initiale est manuelle. Aucun nouveau mécanisme concurrent à `akrat-trust` n’a été ajouté.
- La feature HTTP `stream` requise par l’updater est activée uniquement sur `akrat-node-updater`, et non sur le manifeste workspace partagé. Le graphe effectif de `akrat-desktop` confirme qu’il ne reçoit pas cette feature.

## Contrôles locaux

Sur Windows, `cargo fmt --all -- --check`, `cargo check --locked --target x86_64-pc-windows-msvc -p akrat-node-updater`, `cargo clippy --locked -p akrat-node-updater --all-targets -- -D warnings` et `cargo test --locked -p akrat-node-updater` réussissent. Les dix tests couvrent la configuration, les URLs d’assets GitHub, la politique stable/manuelle, la réponse de santé, les signatures invalides, la sauvegarde SQLite, une installation simulée avec validation de santé et le retour arrière du binaire/de l’état/de la base après échec.

Le binaire Windows a interrogé l’API du dépôt privé avec l’authentification GitHub locale; aucune mise à jour stable plus récente n’était publiée. Le binaire Linux de la CI a été téléchargé et lancé sous WSL; sa CLI affiche les quatre commandes. Ce contrôle ne simule pas un déploiement systemd.

## Tests réseau

Le test d’intégration `favorite_relay_can_establish_an_open_p2p_path` vérifie un flux chiffré via un relais favori utilisé comme route commune par les deux endpoints. Iroh sélectionne entre les chemins déjà ouverts; il ne promet pas d’ouvrir automatiquement chaque relais mentionné dans une adresse distante. Le classement des chemins direct/favori/autorisé est vérifié par `relay_path_tiers_keep_direct_paths_ahead_of_favorites_and_allowed_relays`. Le test `endpoint_switches_to_an_allowed_relay_after_home_relay_fails` valide le repli et la livraison après panne du relais initial.

## Portée et limites opérationnelles

Windows x64, Linux x64 et Android sont validés par la CI complète du commit `0809f4d1`; le commit final ajoute uniquement deux tests et passe le contrôle ciblé Linux. macOS n’est pas compilé ni validé. Les tests de relais locaux ne mesurent pas la disponibilité de relais publics sur Internet. L’updater Linux n’a pas encore été déployé sur un VPS avec systemd actif, une mise à jour signée disponible, un redémarrage réel et une éventuelle migration de schéma Mailbox. Les tests de transaction utilisent un contrôle de service simulé et des fichiers temporaires; ils ne remplacent pas l’essai sur les exécutables de deux versions différentes. Le mode automatique doit rester désactivé sur les nœuds critiques jusqu’à ces essais opérationnels. La validation CI démontre les builds et tests; le lancement sous WSL ne démontre pas un déploiement en production.
