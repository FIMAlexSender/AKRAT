# AKRAT v0.1.12 · validation et dépendances

État de ce rapport : 13 novembre 2026. Les résultats de build et de test distinguent les contrôles exécutés localement des validations distantes. La publication n’est validée qu’après les jobs Windows, Linux et Android de la CI.

## Architecture livrée

- `akrat-trust` isole les preuves d’identité de relais : défi de 32 octets, URL liée à la signature, signature Ed25519, empreinte SHA-256 et comparaison avec une empreinte approuvée hors bande. Le client réseau est optionnel.
- `akrat-relay` supervise le binaire officiel `iroh-relay` 1.4.1 et expose un service HTTP séparé sur TCP 8090 pour les preuves de défi. L’identité est conservée dans un fichier distinct à permissions restreintes sur Unix. Les requêtes ont une limite de 4 Kio et 16 vérifications concurrentes.
- La Mailbox et le relais restent des processus indépendants; `akrat-node.sh` et `akrat-node.ps1` les supervisent ensemble ou séparément. Les fichiers d’exploitation et l’unité systemd sont inclus dans les archives de plateforme.
- `akrat-core` reste le point de compatibilité pour les structures cryptographiques et de coffre existantes. La version ne réécrit ni AES-GCM, Argon2id, Libsignal/PQXDH, Double Ratchet, Noise, ni le transport Iroh.
- Les images envoyées à un destinataire hors ligne sont découpées en fragments chiffrés de 20 Kio, enveloppés individuellement par le protocole asynchrone de ce destinataire, puis récupérés et authentifiés fragment par fragment. La reconstruction et l’accusé d’image complète n’ont lieu qu’après vérification de toutes les empreintes.
- Le traitement d’image et Markdown devient optionnel dans `akrat-core`. `akrat-mailbox` utilise `default-features = false`; il ne compile donc pas les décodeurs d’image ni le parseur Markdown. Les manifestes de pièces jointes chiffrées restent lisibles.
- Les paramètres de relais sont enregistrés dans le coffre avec des valeurs par défaut de migration. Le niveau 1 exige une identité épinglée pour les relais personnalisés. Si aucun relais n’est admis, le réseau reste en mode direct seul; aucun repli vers un relais inconnu n’est fait.

## Audit de sécurité des dépendances

Contrôles exécutés : `cargo audit`, `cargo deny check -W unmaintained -W unsound`, `cargo machete`, `cargo metadata --locked` et `cargo tree` pour les sept combinaisons de cible ci-dessus.

- RustSec : 0 vulnérabilité de sécurité trouvée dans le Cargo.lock au 12 novembre 2026.
- Licences, sources et interdiction de dépendances wildcard : contrôles `cargo deny` réussis.
- Dépendances directes inutilisées : aucune détectée par `cargo machete`.
- `cargo deny` retourne le code 0 et laisse visibles ses avertissements : 83 duplications, 4 avertissements de crates non maintenues, 2 unsoundness.
- `cargo audit` plus récent signale en outre `proc-macro-error2` (RUSTSEC-2026-0173), absent de la version de base de données embarquée dans `cargo deny 0.20.2`.

Les bibliothèques concernées sont transitives. Les retirer au moyen d’une réécriture ou d’un patch local serait plus risqué que leur usage actuel. Les mises à jour de Dioxus, GTK, Libsignal/Libcrux et des macros devront être réévaluées au fil de leurs versions amont. Aucune alerte n’est ignorée dans `deny.toml`.

Les décomptes initiaux/final d’exécutables n’ont pas été comparés : aucun artefact v0.1.11 construit avec le même toolchain, mêmes features, même système et mêmes flags n’était présent dans le checkout au moment de la mesure. Un tel chiffre serait trompeur. Les builds finaux Windows sont rapportés par les artefacts CI et leurs sommes; les mesures de taille de référence v0.1.11 restent à collecter dans un environnement strictement identique.

## Confiance et limites

- Niveau 0 : les relais non épinglés ne sont utilisables que si la politique locale l’autorise.
- Niveau 1 : signature de défi Ed25519, défi frais, URL relay liée à la signature, clé comparée à une empreinte fournie hors bande, pin persisté dans le coffre. Une clé différente n’écrase pas silencieusement le pin.
- Niveau 2 : provenance signée d’une distribution officielle non implémentée.
- Niveau 3 : attestation matérielle non implémentée. Aucune empreinte déclarée par le serveur n’est présentée comme preuve du code en cours d’exécution.
- Rotation authentifiée des clés de relais, réputation, preuves de faute, partage décentralisé et quarantaine ne sont pas implémentés dans cette version.
- Le transport Iroh conserve le chiffrement/authentification du canal. Le relais peut voir les adresses IP et métadonnées de connexion, retarder, rejouer au niveau réseau ou bloquer le trafic. La Mailbox reste le mécanisme distinct de livraison lorsque le correspondant est hors ligne.

## Vérifications

Le test `akrat-core/tests/relay_transport.rs` crée un vrai serveur Iroh local et deux endpoints qui désactivent les transports IP directs; un flux AKRAT y est transmis par le relais et reçu. Le test `runtime::tests::iroh_transport_connects_by_peer_id_and_keeps_noise_identity_pinned` couvre le chemin direct et l’authentification Noise. Les tests Mailbox multi-processus existants couvrent la fédération et la livraison différée. Le scénario `async_mailbox::tests::desktop_helpers_deliver_offline_message_and_confirm_delivery` envoie également des images de plusieurs fragments dans un DM et un groupe pendant que les destinataires sont hors ligne; il vérifie la reprise, la déduplication entre copies fédérées, les reçus par fragment et le déchiffrement après reconstruction complète. Les tests confirment que les nouveaux fragments tiennent dans les limites de dépôt et de récupération Mailbox.

Validation locale Windows de la base v0.1.12 (12 novembre 2026) : `cargo build --locked --release` produit les cinq exécutables Windows : desktop, CLI, Mailbox, wrapper relais AKRAT et serveur Iroh. Tailles observées à cette date : 33 556 992, 16 452 608, 5 285 888, 3 423 232 et 9 655 808 octets. La première compilation de tests parallèle avait épuisé la mémoire de cette machine; les vérifications complètes avaient ensuite passé séquentiellement.

Validation locale Windows de la branche de finalisation (13 novembre 2026) : `cargo fmt --all -- --check`, `cargo check --locked --workspace --all-targets`, `cargo clippy --locked --workspace --all-targets -- -D warnings` et `cargo test --locked --workspace` passent. Les tests comptent 95 cas, dont le transfert hors ligne des images directes et de groupe réparties en plusieurs fragments. Une vérification CI distante sur cette version de la branche reste nécessaire pour valider Linux et Android; elle n’est pas confondue avec le succès antérieur du tag.

Validation CI du tag `v0.1.12` : les jobs Linux, Windows et Android ont réussi, incluant tests, lint, audit et génération de l’APK signé. Le job de publication automatique a échoué après ces validations, car il exécutait `cargo-cyclonedx` sans installer Rust. La Release a été assemblée depuis les artefacts de ce run et publiée sur GitHub avec 18 assets. Les 17 fichiers référencés par `SHA256SUMS` ont été vérifiés localement; les empreintes SHA-256 calculées par GitHub pour les assets correspondants concordent. Le workflow installe maintenant Rust dans le job de publication pour les prochaines versions. La correction ne modifie pas le tag ni les binaires v0.1.12. macOS n’est pas une cible de cette release.
